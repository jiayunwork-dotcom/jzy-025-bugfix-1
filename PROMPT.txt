这套稳度评估服务已经在我们这边跑起来了：喂一条等间隔的钟差或分数频率序列进去，它算重叠 Allan 方差、读局部斜率、标噪声类型，每次提交成功后会回一个受理凭据；之后凭这个凭据去读接口，就能把当次算出来的那条稳定度曲线原样拉回来。功能面我们验过一圈，重叠估计、区段识别、按凭据回读这些都对得上，问题出在“提交没成”这条路上。

我们上游有个批处理器，它提交完记录段之后，是拿返回的 HTTP 状态码来判这次到底成没成的：状态码落在成功那一档，就把这份记录号收进“已算好”的清单接着往下走；落在客户端出错那一档，才会把这条挑出来、记进待人工看的队列。这个约定一直用得好好的，直到最近发现一批本该被拒的提交，全被批处理器当成算好了放了过去。

翻了下这些提交：有的把采样间隔填成了 0 甚至负数，有的序列短得还不够服务钉死的下限，有的干脆缺字段、或者序列里混了非有限数。这些提交进到服务里，服务本身其实判对了——取回来看，记录都进了失败态，也写清了为什么失败，没有编一条看着完整的假曲线糊弄人。可就是这些明明失败的提交，POST 回来的 HTTP 状态码报的是“已创建”，跟成功提交用的是同一档。批处理器只看状态码，自然就把它们和真正算好的记录一视同仁地收了进去，等到下游取回曲线才发现是空的、报错，链路已经跑出去老远。

我要的是：提交失败时，HTTP 状态码本身就得如实说明这次没成，而不是只在响应体里塞一个 failed 字段、状态码却还报成功。换句话说，光看状态码就能把“算好了”和“没算成”这两拨分开，不用再去抠响应体。成功提交该是什么状态码就还是什么，别动；失败提交要落到表示这次请求没被接受的那一档去。

复现很直接：起服务后，往提交接口发一条采样间隔为 0（或负数）的记录，再发一条点数不够下限的记录，看它们回来的 HTTP 状态码——现在这两条和一条正常成功的提交拿到的是同一个码。修好之后，这两条失败提交的状态码要变成表示请求出错的那一档，而正常成功的那条状态码不变；两种情况下响应体里原有的记录号、失败原因该带的还得带，取回接口看到的记录内容和落盘行为也不能受影响。别把已经判对的失败态逻辑推倒重写，就把对外这层状态码的口径摆正，让状态码和记录的真实结局对上。技术栈沿用现有实现，改完在现有容器里一键起服务，配套测试要能锁住“失败提交的状态码不再是成功那一档”。
